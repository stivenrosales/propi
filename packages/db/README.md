# @propi/db

The Postgres adapter: Prisma schema, hand-written SQL migrations, and the `@propi/app` ports
(`UnitOfWork`/`Tx`, `Reader`, `Directory`, plus production `Clock` and UUIDv7 `Ids`).

## How it keeps the ledger correct

- **Append-only** (S30): triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `ledger_entry` and
  `domain_event`. `command_log` allows one change per row: the claim's `running -> done`.
- **Signs from EFFECTS** (G1): one `CHECK` per entry kind, generated by `ledgerCheckConstraints()`
  from core `EFFECTS`. A test fails if the migration and the generator disagree.
- **Locks** (G4): each unit of work is one interactive transaction at READ COMMITTED that takes
  `pg_advisory_xact_lock(hashtextextended('<workspace>|<key>', 0))` on the sorted lock keys first.
- **Claim first** (G2): `INSERT INTO command_log ... 'running' ON CONFLICT DO NOTHING`. A concurrent
  duplicate waits on the uncommitted row, then replays the stored result.
- **Nothing derived is stored**: balances and allowance are SQL sums over `ledger_entry`.
- **Shop writes are compare-and-set** (S46, S49, S51, S57): redemptions and collabs move with
  `UPDATE ... WHERE state = <from>`, stock with a conditional `stock + delta >= 0`; when a write
  changes 0 rows the whole unit of work (claim, entries, events) rolls back. `CHECK (stock >= 0)`
  and a unique index (one redemption per collab) back them up.
- **Module state** (migration `20261125020000_modules`): shop (`module_config`, `reward`,
  `reward_variant`, `redemption`, `collab`) and engagement (`award_rule`, `quest*`, `sticker*`,
  `member_avatar`, `milestone_profile`, `pairing_*`). Engagement stores read through the running
  unit's transaction while one is active, so a locked unit never needs a second pool connection.

## Commands

```sh
docker compose -f deploy/docker-compose.dev.yml up -d --wait   # Postgres 17 on localhost:55433
export DATABASE_URL=postgresql://propi:propi@localhost:55433/propi
pnpm --filter @propi/db db:migrate    # prisma migrate deploy
pnpm --filter @propi/db db:status     # prisma migrate status
pnpm --filter @propi/db generate      # prisma generate (also runs on install)
pnpm --filter @propi/db test:db       # db suites only; fails without DATABASE_URL
pnpm test                             # db suites run only when DATABASE_URL is set
```

Each db test file creates its own database (`propi_test_<random>`), migrates it with
`prisma migrate deploy`, and drops it afterwards.

## Usage

```ts
import { createApp, engagementHandlers } from "@propi/app";
import { createDbEngagementStores, createDbIdentityStore, createDbPorts, createPrismaClient } from "@propi/db";

const prisma = createPrismaClient(process.env.DATABASE_URL!);
const ports = createDbPorts(prisma, { giftCards }); // giftCards: the S108 provider, or omit
const app = createApp(ports, {
  handlers: engagementHandlers({ reader: ports.reader, directory: ports.directory, ...createDbEngagementStores(prisma) }),
});
const identities = createDbIdentityStore(prisma); // S107
```

## Adding tables

Add a new migration folder under `prisma/migrations/` with hand-written SQL, mirror the table in
`prisma/schema.prisma`, and check there is no drift:

```sh
pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```
